# 冷链仓月台停机月报

宁波澜港冷链一号仓设备保障组。一号仓有 D01、D02、D03 三座冷链月台。值班主管按入库预约编制排班，维修班记录保养和故障，仓配主管按月核对月台可用率并安排维修窗口。

将月台班表、计划保养单和故障停机台账合在同一份 CSV，每行记录同一月台的一段班次或停机时间，编号保留原系统单号。 向仓配运营月报组交付全仓排班加权可用率、逐月台小计和可按月台与来源编号追查的区间 CSV。

- 交接重叠班次和重复导出的工单会在 Excel 汇总中重复累加。
- 停机跨开班时间或跨月底时，手工截取容易把班外时间扣入可用率。
- 班组按月台百分比做简单平均，复核人员很难从月报回查同一时段的保养单和故障单。

## 六个业务模块

1. 月台运行总览
2. 班次停机台账
3. 停机工单修订（月报寄出后的改期/撤销补报与重编）
4. 月报口径与计算
5. 月台区间追溯
6. 可用率复核
7. 月报重编与版本（受影响月份一次性切换、按工单核对停机秒数）
8. 月报分发与收件箱（历史版本原版下载、补发去重）

## 月报寄出后的工单修订

维修班在月报寄出后仍会补报停机工单的改期或撤销，系统按以下规则闭环处理：

- **修订识别**：按「月台 + 停机类型 + 单号」识别同一工单，修订号越高越新；乱序到达的记录以最高修订号为准。
- **撤销终态**：撤销是终态动作，撤销后补送的同单号旧记录（修订号不高于撤销号）一律拒收，工单不能恢复。
- **重算范围**：改期移出原月份时，旧月份与新月份都进入同一次重编批次；受影响月报在批准时一次性原子切换。
- **失败保留**：重编失败保留全套旧版月报，重试只补算失败月份，已成功月份和已发布内容不重复发布。
- **版本与下载**：每次切换生成新月报版本（v1、v2……），历史版本行永久保留，已寄出的旧版仍可按原版 CSV 下载。
- **仓配核对**：重编详情与版本页按工单展示班内/月内停机秒数的前后变化与月份级合计对比。
- **补发去重**：切换后向该月份的历史收件组补发新版，同批次同月份同收件组只入箱一份。

修订 CSV 表头为 `dock,kind,record_id,revision_no,action,start,end`；`action` 为「改期」或「撤销」，撤销行的起止时间留空。登录后可在「停机工单修订」页下载修订样例 CSV。

## 工作剧本

1. 11 月 2 日 08:20，值班主管查看 10 月三座月台的月报工作台，按 99% 的可用率目标准备复核。
2. 08:35，台账员下载并导入 `ningbo-dock-downtime-2026-10.csv`，核对 99 条班次与停机记录，包括 D03 的 9 月 30 日夜班。
3. 08:45，设备保障组选择 2026-10 和 99% 目标运行月报，确认全仓排班共 710 小时。
4. 09:00，维修班查看 D01 在 10 月 14 日 13:50 至 14:25 的 35 分钟班内重叠，并追溯 P-1014-01、U-1014-01、U-1014-02。
5. 09:20，仓配主管复核 D02 的 195 分钟非计划停机和 10 分钟班外停机，记录其低于 99% 的原因。
6. 09:40，批准并导出含全仓、月台和区间三层明细的 10 月 CSV，安排 10:00 投递给仓配运营月报组。
7. 11 月 3 日 10:10，维修班补报 U-1019-01 改期到 11 月、U-1014-03 撤销等修订；分析员导入修订 CSV，系统自动把 2026-10 与 2026-11 排入同一重编批次。
8. 10:25，复核员在重编批次页按工单核对停机秒数变化，批准后两个月月报一次性切换，旧版仍可下载，收件箱按历史收件组补发新版且不重复。

## 算法与复核

以仓库本地时间 UTC+08:00 按自然月裁切，按秒计算半开区间。同月台班次与各类停机分别取并集，班内停机与班次求交，计划和非计划重叠归非计划。全仓按可用秒合计除以排班秒合计。

月份没有有效班次、记录字段或起止时间无效、同月台同类型同编号对应多个区间时，按提示核对月台班表、原始单号或报告月份后重算。 复核问题为「班次、停机重叠归类和跨月扣减是否与原台账一致，低于目标的月台是否已有复核记录？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `dock` | 月台编号 | str |
| `kind` | 记录类型（班次、计划停机、非计划停机） | str |
| `record_id` | 原始记录编号 | str |
| `start` | 开始时间（YYYY-MM-DD HH:MM:SS） | str |
| `end` | 结束时间（YYYY-MM-DD HH:MM:SS） | str |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18299`
- API 文档 `http://127.0.0.1:19299/docs`
- 数据库端口 `17799`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、登记工单修订、运行分析、重试重编、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、批准重编切换、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告与历史版本、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、MySQL 8.0 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
